Order-book collector

A Rust service for Polymarket and Kalshi · Abhinav Pangaria · take-home challenge, October 2026

It subscribes to every live market on a prediction-market exchange, keeps an L2 order book for each one, and writes every price-level change, plus a snapshot of every book once a minute, in the challenge's aligned SBE format. Every file it writes can be replayed to prove the books are exact.

The pipeline

One engine, five stages. Only the first two know which venue they are talking to; that seam is the ExchangeAdapter trait (Ext 3).

  1. 01DiscoveryLists every live market at start and every 10 minutes, and follows the venue's listing and resolution events in between. New markets join; resolved ones are dropped.
  2. 02Shards and socketsMarkets are split into shards of 2,500 tokens. Each shard gets two websockets on different edge servers (Ext 1), so losing one socket or one edge loses nothing.
  3. 03DecodeTokio workers read the sockets and turn the venue's JSON into a common event: a price, a size and a timestamp.
  4. 04Core threadsEach core thread owns whole markets. It applies events to flat sorted books, chooses which replica is the source, and checks each book against the venue's hash.
  5. 05WriterEncodes updates and snapshots with the template's SBE helpers into 64 MiB chunks. Each chunk is written as it fills, then the file is rotated off the hot path.

When something goes wrong

Each case below has a test that injects the fault against a mock venue, and most were also seen live.

A socket drops
Its replica is already the source or becomes it. A snapshot is written at the switch, so the output stays exact. The socket reconnects with backoff.
A socket goes silent
Replaced once a peer has been ahead for 3 s (--lag-ms). Quiet sockets are reconnected; every socket is recycled hourly, make-before-break (Ext 2).
A token goes quiet
Per-token rate checks resubscribe only tokens that are quiet for their own rate, with a wait that doubles on each strike (Ext 2).
A book is corrupted
The venue's book hash disagrees; the book is resynced from a fresh snapshot.
The process dies
--supervise restarts it in about a second and keeps every whole chunk of the open file.
Ctrl-C or SIGTERM
Closes every websocket, writes the last chunk, closes the file.

How it got here

The first build was correct but small. Each run at a bigger scale or a harder fault found the next limit; each limit got a fix and a measurement. The charts follow the same metric across the runs, labelled with the fixes that landed before each one.

Reading the charts: each point is one run. The second line under a run names the fixes that came before it (numbers match the list below). Hover or tap a point for its value; each chart has a table view.

The fixes

In the order they were found. Each line says what hit the limit, how it was found, and what the fix moved.

  1. #1
    Laptop link behind a VPN, 3.3 Mbit/s
    Run 4 collapsed into a reconnect storm. Moved to a cloud host near London; added a global outage backoff.
    wire p99: minutes → 173 ms
  2. #2
    Coverage stuck at 47.5k of 131k tokens
    Coverage grew one shard per 30 s, then stopped. The open limiter now reads the current gap; books that never arrive are re-asked.
    47.5k → 96k, later 100% placed
  3. #3
    Socket cap and rate-limited lookups
    Cloud 1 left 196k tokens unplaced and 102 lookups got 429s. The cap is sized to the universe; lookups are batched with backoff.
    250k → 459k placed, 0 429s
  4. #4
    Timers starved by inbound messages
    Cloud 2 printed one status line in 5 minutes. Timers run first; inbound is taken in batches of 256.
    p99 71 s → 524 ms
  5. #5
    The hash check took 45% of the core
    A perf profile showed allocation per level and a full rehash per candidate price. Hash once, copy the partial state, format without allocating.
    18.9k → 32.3k updates/s
  6. #6
    One core thread at 99.9%
    Per-thread CPU from /proc. K core threads now each own whole markets.
    99.9% → 50–90% per core
  7. #7
    Ext 2 over-tuned
    Soak 1 made 400k resubscribes in 90 minutes. Quiet detection became rate-aware, and the wait doubles on each strike.
    resubscribes cut to the truly quiet tokens
  8. #8
    Hashing standbys and a full lag walk
    A whole-process profile. Only the source replica is hashed; the lag check keeps an incremental candidate list.
    core CPU 50–60% → 31–38%
  9. #9
    Rotation fsync stalled every reader
    Profile 2 had 330 s and 1,153 s blocked in rotation windows. A finisher thread fsyncs and renames off the writer.
    blocked time at rotation → 0
  10. #10
    Hot-shard splitting caused a reconnect loop
    The A/B showed 11–19× the disconnects: the venue closes a socket whose assets have all resolved. Resolved tokens are dropped; splitting is opt-in.
    loop gone
  11. #11
    Memory at 2.8–3.3 GB
    An offline bench found 7.6 KB of heap per token. mimalloc, flat sorted books, inline replicas, one symbol per token, lazy hash state, FxHash.
    RSS 3.0 → 1.73 GB
  12. #12
    Disk stalls could reach the books
    The 2.5-hour soak had 8 writer waits of 1–1.5 s. A byte-bounded 256 MiB writer queue absorbs them.
    8 waits → 0
  13. #13
    The receive time included TLS and parsing
    --kernel-ts reads the kernel's arrival time (SO_TIMESTAMPNS) and reports the host's own delay.
    host delay measured: p50 ≤ 32 µs on AWS
  14. #14
    --pin started one core thread instead of two
    Found in the gate log. CPUs are counted once, before pinning.
    2 core threads, 281k / 280k tokens
  15. #15
    One tokio worker for about 450 TLS sockets
    Host delay was 4× worse in gate 2. A 5-minute A/B of three layouts; io workers now default to at least 2.
    host p99 8–16 ms → 4–8 ms
  16. #16
    A kill -9 without the supervisor lost the file
    Chunks were written at the end. Each chunk is now written in place as it fills.
    data kept after kill at 120 s: 0 → 119.8 s

Ruled out by measurement: the TCP source port (Ext 4, Experiment 3), hyperthread siblings for the core threads, and the ~1% of tokens with no book (the venue has none).

Where the time goes

Three numbers, each with a different clock problem. Only the last one is time spent inside the collector.

recv − exch
Kernel receive time minus the venue's event timestamp. Includes the venue's own processing, the network, and any clock offset, so it needs a synced clock (chrony on AWS).
behind
How long after the first socket to deliver an event another socket delivered it. Both times are on our clock, so it compares sockets and edges without any offset.
Host delay
Kernel receive to the collector reading the frame (--kernel-ts). This is the part the collector controls.
8–9 msrecv − exch p50, full universe, AWS London
≤ 32 µshost delay p50, every 30 s window
≤ 8 mscore queue p99

The four experiments

1 · Many sockets, same tokens
Eight sockets on 400 markets for 20 minutes, two edges. The best socket was 1.4 ms behind the first on average and the worst 10.3 ms; the faster edge was about 2.5 ms better. built in
Replicas use different edges, and the source is the replica that is ahead.
2 · A speed-aware source
--fast-source scores sockets and prefers the faster one. It moved means by tenths of a ms and made one p99 worse. opt-in
3 · Does the source port pick the path?
Twelve sockets over six rounds, six on fixed ports. Rank correlation round to round +0.27, p ≈ 0.10: no reliable effect. ruled out
4 · Tuning on AWS
Five A/B rounds: --fast-source, 4 replicas, a 1 s failover window, kernel busy polling. The best gain was under 1 ms at p50. defaults kept

Conclusion. The collector adds microseconds; the milliseconds are the venue and the path to it. The one lever that moved the median by a lot is the region: London 7 ms, Ireland 12 ms, Virginia 43 ms on the same markets at the same second.

Not tried yet

Unit tests
Kalshi's example frames from its docs; signatures with both key types checked over the exact signed string.
End to end, offline
A mock Kalshi venue: the real binary, two replicas, then verify. Cases: a baseline, a seq gap, a new listing.
Live, demo environment

Both venues together

Run it

Needs stable Rust. One command builds, replays the committed sample, runs the offline tests and collects two minutes of live Polymarket data:

./demo.sh

Polymarket, by hand

cargo build --release --bins
./target/release/collector --out ob.sbe --max-markets 2000 --duration-secs 120
./target/release/verify ob.sbe

Kalshi

Put a key in a gitignored .env (KALSHI_API_KEY_ID, KALSHI_PRIVATE_KEY_PATH), then:

./demo.sh kalshi                # production
KALSHI_DEMO=1 ./demo.sh kalshi  # demo environment
./demo.sh both                  # both venues at once

Elsewhere

Docker
docker build -t collector ., then run it with a volume for the output.
GitHub Codespace
The repo has a devcontainer for a 4-core machine; run ./demo.sh in it.
